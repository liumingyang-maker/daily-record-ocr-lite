# 面向用户的证据优先配方工作流设计

- 日期：2026-07-27
- 状态：已完成会话设计确认，等待用户审阅书面规格
- 分支：`feat/evidence-first-product-workflow`
- 基线：`origin/master` (`8d5f3b2`)

## 1. 背景

当前网页把内部识别结构直接暴露给普通用户：任务列表显示任务号、Provider 和英文状态；任务详情要求用户理解 Field ID、OCR、VLM、历史候选、BBox 和 Schema；任务详情与识别结果又形成两个相互重叠的审查入口。知识库则以物料字典为中心，无法表达“客户 + 产品/牌号 + 日期”下持续追加的配方历史。

真实手写样图的业务结构是：页面顶部为客户，下面是产品或牌号；同一产品下有多条按日期记录的配方，每条配方包含物料、数量、可能的单位和可选工艺参数。产品要解决的核心问题不是让用户调试识别引擎，而是让用户对照原图，快速确认机器整理出的业务记录。

## 2. 目标

1. 把整站的信息架构改为普通用户能够理解的业务流程。
2. 用证据优先的配方卡片替代字段级开发者表格。
3. 允许用户编辑、增加、删除和排序配方、物料及工艺参数。
4. 要求客户、产品/牌号和日期完整后才能确认配方。
5. 全部配方确认后，以正式 `FinalResult` 为数据源，事务性写入知识库。
6. 知识库按客户、产品/牌号和日期展示历史；新日期只追加，不覆盖旧记录。
7. 保留现有任务、知识库和本机配置数据，并兼容已有URL。

## 3. 非目标

- 不修改 OCR、视觉模型、Prompt、超时、缓存或识别 Pipeline。
- 不包含 OCR 预热、多核优化、Mac 适配或模型性能优化。
- 不在普通页面提供完整 JSON 编辑器；高级诊断仍可保留只读入口。
- 不在本任务中合并、Tag 或发布版本；先创建并验证独立 Draft PR。
- 不重做为 React、Vue 等新前端框架，继续使用 FastAPI、Jinja、原生 JavaScript 和现有 CSS。
- 桌面安装包由配套规格 `2026-07-27-desktop-installers-design.md` 单独实施；本规格只提供其需要的稳定应用和数据目录接口。

## 4. 统一业务语言

普通页面只使用以下术语：

- 客户：原“公司”。
- 产品/牌号：如 `G30A`、`PA66T30`。
- 配方记录：某客户、某产品/牌号在某日期的一条配方。
- 物料：配方中的原料或助剂。
- 工艺参数：配方下可选的工艺名称、数值和单位。
- 原图证据：用于核对识别结果的整图或裁剪图。
- 需要确认：存在空值、冲突、低可信或缺少必填项。

`Field ID`、`OCR`、`VLM`、`BBox`、`Schema`、Provider 和内部状态码只允许出现在折叠的高级诊断中。

## 5. 信息架构和路由

主导航调整为：

1. 开始识别：`/`
2. 识别记录：`/jobs`
3. 配方知识库：`/knowledge`
4. 设置：`/settings`

`/jobs/{job_id}` 是唯一的任务进度、审查和完成页面。已有 `/jobs/{job_id}/result` 返回重定向到 `/jobs/{job_id}#review`，避免旧书签失效但不再维护第二套结果界面。

全局页眉不再在每个页面重复显示流程标语；流程说明只保留在首页。页脚保留版本号，高级诊断入口放到设置页。

## 6. 首页与识别记录

### 6.1 开始识别

首页唯一主任务是上传图片并开始识别：

- 文件选择后立即显示缩略图。
- 每张图片可单独旋转、删除和调整顺序。
- 默认对每张图片自动纠正方向，而不是用一个下拉框影响整批图片。
- 明确提示“多张图片将作为同一批记录识别”。
- 主按钮为“开始识别”；系统未配置时按钮禁用并给出“完成设置”入口。
- 技术引擎信息收进“系统状态”折叠区。

### 6.2 识别记录

新增独立记录列表，首页只显示少量最近记录。列表列为：

- 客户
- 产品/牌号
- 配方日期范围
- 图片数
- 用户状态
- 创建时间
- 下一步操作

任务号、模型和详细耗时放入行内“高级信息”。当业务信息尚未识别出来时，用“正在整理”占位，不显示空的 `- / -`。

## 7. 用户状态和错误信息

内部状态映射为：

| 内部状态 | 用户状态 | 主操作 |
|---|---|---|
| UPLOADED / PREPARING / RECOGNIZING | 正在识别 | 查看进度 |
| REVIEW_REQUIRED | 需要确认 | 继续确认 |
| READY | 可以导出 | 导出 Excel |
| EXPORTED | 已完成 | 下载或查看 |
| FAILED / FAILED_SCHEMA | 识别失败 | 查看原因并重试 |

任务处理期间显示四步进度：处理图片、读取手写内容、整理配方、等待确认。失败提示必须说明用户可以采取的下一步，例如“视觉服务没有返回结果，请检查连接后重新识别”。内部错误类别、HTTP 状态和 request ID 放在可复制的脱敏诊断区。

## 8. 证据优先配方审查工作台

### 8.1 页面结构

页面顶部是业务摘要：客户、产品/牌号、图片数、配方数、待确认数及当前下一步。任务号、模型、缓存和耗时默认折叠。

主体先显示“需要你确认”的卡片，再显示折叠的“其他已识别配方”。用户可切换“只看待确认”和“查看全部”。不再渲染字段级审查大表。

### 8.2 身份信息卡

每个客户和产品/牌号组合先显示身份信息卡：

- 左侧显示相应原图或证据区域。
- 右侧显示可编辑的客户和产品/牌号。
- 修改后自动保存。
- 同页多配方共享该身份时，修改同步作用于对应配方组。

### 8.3 配方卡片

每条配方卡片包含：

- 标题：产品/牌号、配方编号、日期和确认状态。
- 左侧：原图证据，支持放大查看；存在字段坐标时突出当前内容，没有坐标时展示整图。
- 右侧：可编辑的配方编号和必填日期。正式日期统一保存为 `YYYY-MM-DD`；只识别出月日时，用户必须补全年份。
- 物料表：序号、物料名称、数量、单位。
- 工艺区：可选的参数名称、数值和单位。

卡片支持：

- 编辑所有业务值并自动保存。
- 添加、删除和调整物料顺序。
- 添加、编辑和删除工艺参数。
- 添加漏识别的配方。
- 删除错误配方；删除配方前必须确认。
- 删除物料或工艺项后显示即时“撤销”操作。

这里的删除只作用于尚未完成审查的当前任务。已经写入知识库的历史配方不能被这组操作删除或覆盖。

不显示字段ID、候选来源、识别引擎名称或英文审查状态。对于冲突或低可信字段，只用“请对照左侧原图确认”提示，并突出对应输入框。

### 8.4 确认规则

每张卡片使用“确认这条配方”。满足以下条件才可确认：

- 客户非空。
- 产品/牌号非空。
- 日期是有效日期。
- 至少有一个物料。
- 每个物料名称和数量非空。
- 所有冲突、空值和低可信字段已由用户确认或修改。

阻断信息必须指向具体业务对象，例如：“待确认：联创 / G30A / 配方2 缺少日期”。修改已确认卡片时，系统自动撤销该卡片的确认状态，要求重新确认。

用户点击“确认这条配方”表示已经对照证据接受卡片当前全部可见值。服务层在不篡改字段值的前提下，把卡片中仍为冲突或低可信的非空字段标记为 `MANUAL_CONFIRMED`，把允许为空的可选字段标记为 `MANUAL_CONFIRMED_EMPTY`；必填空值仍然阻止确认。这样正式 `FinalResult` 的 Ready Gate 与整卡确认保持一致。

所有卡片确认后，页面唯一主按钮变为“完成审查并保存到知识库”。保存成功后再显示“导出 Excel”。

## 9. 正式数据流和接口边界

### 9.1 数据原则

`FinalResult` 继续是业务内容的唯一正式数据源。所有页面编辑都先通过服务层修改 `FinalResult`，Excel 导出和知识库写入均重新读取同一份正式结果。页面不得维护一份与 `FinalResult` 分叉的业务副本。

卡片确认属于工作流状态，保存在独立的 `review_state.json`。每条确认记录包含配方ID和内容摘要哈希；业务内容变化后哈希不匹配，确认自动失效。该文件不替代业务数据。

### 9.2 面向业务的接口

新增一组业务级接口，由审查服务统一校验并更新 `FinalResult`：

- `GET /api/jobs/{job_id}/review`：返回审查页视图模型。
- `PATCH /api/jobs/{job_id}/identity/{group_id}`：更新客户或产品/牌号。
- `PATCH /api/jobs/{job_id}/formulas/{formula_id}`：更新编号或日期。
- `POST /api/jobs/{job_id}/formulas`：新增配方。
- `DELETE /api/jobs/{job_id}/formulas/{formula_id}`：删除配方。
- 物料和工艺参数的新增、修改、删除及排序子资源接口。
- `POST /api/jobs/{job_id}/formulas/{formula_id}/confirm`：确认单条配方。
- `POST /api/jobs/{job_id}/finalize`：执行完整 Gate 并写入知识库。

现有字段级接口保留用于兼容和高级诊断，但普通页面不再直接调用。

### 9.3 自动保存与并发

输入框在失焦或短暂停顿后自动保存，页面显示“保存中 / 已保存 / 保存失败”。请求携带当前结果版本；服务端发现版本已变化时返回冲突，页面重新加载最新值并提示用户，避免两个窗口互相覆盖。

## 10. 知识库模型与写入规则

### 10.1 非破坏迁移

保留现有 `customers`、`products`、`formulas`、`formula_items`、别名和修正日志。通过有版本号的数据库迁移新增：

- 配方日期、配方编号、确认时间。
- 来源任务ID、来源配方ID和来源图片序号。
- 修订来源ID，用于保留后续修改历史。
- 工艺参数表。
- `(source_job_id, source_formula_id)` 唯一索引，保证重复完成同一任务不会重复写入。

迁移前为本机知识库创建时间戳备份；迁移失败时回滚，不删除现有数据库。旧配方继续显示，并标注“历史数据未记录日期”。

### 10.2 事务写入

`finalize` 执行顺序：

1. 重新加载并验证 `FinalResult`。
2. 验证每条配方确认哈希仍有效。
3. 验证客户、产品/牌号、日期和物料必填项。
4. 在单个 SQLite 事务内创建或匹配客户和产品，再追加配方、物料和工艺参数。
5. 全部成功后把任务置为 `READY`；任一失败则数据库回滚，任务仍为“需要确认”。

同一客户和产品/牌号的新日期永远新增历史记录，不更新旧配方。对已保存记录进行后续修正时创建带 `revision_of_id` 的新记录，旧记录保持可追溯。

## 11. 配方知识库页面

知识库默认结构是“客户 → 产品/牌号 → 日期时间线 → 配方详情”。支持按客户、产品/牌号和日期搜索。

产品时间线显示每次配方的日期、编号、物料数量和工艺参数数量。详情页可查看物料、数量、单位、工艺参数、来源任务和原图证据。用户可选择两个日期进行差异对比，并导出单条配方或某产品的完整历史。

现有物料、单位、分类、别名和批量导入功能保留到“物料字典”二级区域，不再占据知识库首页。

知识库不提供直接覆盖历史记录的编辑操作。必要修正走“创建修订”，确保审计链完整。

## 12. 设置和首次配置

默认设置页只显示：

- AI识别服务是否已连接。
- 当前模型。
- API Key 是否已配置。
- “测试连接”。
- OCR 引擎是否正常。
- “运行系统检查”。

Provider、Base URL、Endpoint、Device、最小置信度和JSON能力细节放进“高级设置”。测试结果用用户语言呈现；脱敏技术结果放在“复制诊断信息”中，不直接铺满页面。

首次配置向导使用中文步骤，不再出现 `Step`、`Preset`、`Provider`、`tier`、`Device` 等未解释的术语。演示模式入口与真实模式明确区分，不能让固定结果看起来像真实识别。

## 13. 视觉、响应式与可访问性

- 每个页面只保留一个最重要的实心主按钮。
- 绿色表示完成，橙色表示需要确认，红色只用于失败或危险删除。
- 表单标签始终可见，不能只依赖 placeholder。
- 错误与待确认状态除颜色外还必须有文字和图标。
- 键盘可以到达卡片、输入框、折叠区和按钮。
- 窄屏下证据图位于表单上方，操作按钮固定在卡片底部；不出现横向字段大表。
- 用户输入按文本处理并做HTML转义，避免识别内容形成脚本或危险Excel公式。

## 14. 测试策略

实现按 TDD 分为以下验证层：

1. 数据模型：数据库迁移、备份、事务回滚、历史追加、幂等和修订链。
2. FinalResult 服务：身份、日期、物料、工艺和配方增删改排序；修改后确认失效。
3. Gate：缺日期、缺客户、缺产品、空物料和未确认字段均阻止完成。
4. API：业务级接口成功、校验失败、版本冲突、撤销和不存在资源。
5. 页面：用户导航、中文状态、默认只显示待确认、无开发字段表、设置高级折叠。
6. 完整用户旅程：上传夹具 → 生成结果 → 编辑 → 单条确认 → 完成 → 知识库时间线 → Excel。
7. 回归：现有非真实OCR测试、Ruff、`git diff --check`，并确保已有字段级API和旧结果URL兼容。

真实识别验证使用用户本机私密配置和新任务，不覆盖旧任务；测试输出和审计报告不得包含API Key或完整业务响应。

## 15. 验收标准

- 首页可预览、逐图旋转、删除和排序多张图片。
- 普通页面不再出现 Field ID、OCR/VLM候选、BBox、Schema或英文任务状态。
- 任务详情和结果页合并为一个证据优先工作台。
- 默认只展开冲突、空值、低可信和缺日期的配方。
- 用户可编辑、增加、删除和排序配方、物料和工艺参数。
- 缺少客户、产品/牌号或日期时，提示精确指向相应配方且禁止确认。
- 所有修改写入正式 `FinalResult`，并继续作为Excel唯一数据源。
- 完成操作事务性写入知识库，失败不产生半条记录。
- 同一客户、同一产品/牌号的新日期按时间追加，旧记录不被替换。
- 知识库可以按客户、产品/牌号、日期查看和比较配方历史。
- 设置页默认面向普通用户，高级连接参数和诊断信息折叠。
- 旧任务数据、本机配置、知识库和旧URL均得到保留。
- 全部新增测试、现有非真实OCR测试、Ruff和差异检查通过。
- 提交、PR和最终交付均附可复制的脱敏审计报告。

## 16. 实施边界

实现使用独立分支和工作树，不修改用户当前运行目录中的手工补丁、`data/`、旧Job或私密配置。改版应拆成可验证的纵向提交，但作为一个连贯的 Draft PR 交付。没有完成数据迁移测试、FinalResult Gate、知识库历史追加、Excel回归和整站验收前，不建议合并。
