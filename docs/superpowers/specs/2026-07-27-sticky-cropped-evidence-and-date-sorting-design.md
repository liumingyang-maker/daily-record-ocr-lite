# 配方级裁剪证据与原始日期排序设计

日期：2026-07-27  
状态：用户已批准设计，等待实施计划  
目标分支：`feat/personal-knowledge-layer`（PR #9，继续保持 Draft）

## 1. 背景与已复现问题

当前 OCR 与 Qwen 都读取整张预处理图片，这一点应保留，因为客户、产品、日期和
配方上下文可能位于配方材料区域之外。问题出在审查层：

1. 审查卡片加载整张原图，没有为每条配方生成真正的裁剪证据。
2. `record_bbox` 存在时只叠加红框；当前 Qwen 紧凑合同没有返回
   `record_bbox`，所以真实 Job 甚至没有红框。
3. `.evidence-card` 虽然声明了 `position: sticky`，但祖先
   `.formula-card { overflow: hidden; }` 形成了错误的滚动约束，长配方编辑时
   图片不会按预期跟随视口。
4. Qwen 可返回 `24.7.19` 或 `22/9/27`，而审查页使用
   `<input type="date">`。浏览器只接受 ISO 日期，导致已经识别出的原始日期也
   可能显示为空。
5. 用户要求日期保留原写法，同时系统必须理解具体日期并按时间排序。

现有本地布局算法在两张真实样图上每页只产生一个大记录区域，不能直接声称已具备
配方级裁剪能力。

## 2. 目标

- OCR 与 VLM 继续使用整图识别。
- 每条配方生成与其绑定的裁剪证据，并在桌面审查卡片内跟随滚动。
- 用户始终可以查看完整原图。
- 模型坐标不可信时由本地证据回退；两者都不可靠时静默展示较大安全区域或整图。
- 裁剪只服务于人工对照，绝不修改 FinalResult 业务值。
- 日期在 UI、FinalResult 和 Excel 中保留用户原文。
- 系统另外生成可验证的内部日期排序值。
- 不削弱数量、日期、编号和单位的知识纠偏保护。

## 3. 非目标

- 不把整图识别改成逐配方多次调用 Qwen。
- 不通过裁剪结果自动改写任何材料、数量、日期或工艺字段。
- 本次不增加手动画框编辑器。
- 本次不扩大到 OCR 多核、macOS、安装器或 Pipeline 重构。
- 不改变 PR #9 的 Draft、禁止合并、禁止发布状态。

## 4. 总体数据流

```text
原图
 ├─ 整图预处理 → PP-OCRv6 ───────────────┐
 └─ 整图预处理 → Qwen紧凑业务JSON ───────┤
                                          ↓
                               record-v1 + OCR布局证据
                                          ↓
                         FormulaEvidenceResolver（只定位）
                          ├─ Qwen record_bbox
                          ├─ OCR序号/日期/行位置
                          └─ 安全回退区域
                                          ↓
                           配方裁剪图 + evidence manifest
                                          ↓
                         左侧sticky证据 + 右侧业务编辑
                                          ↓
                         用户确认 → READY → Excel/知识写回
```

## 5. 混合裁剪定位

### 5.1 模型候选

阿里云 qwen3.7-plus 紧凑合同为每条 record 增加可选字段：

```json
{
  "source_image_index": 1,
  "record_bbox": [0.10, 0.18, 0.88, 0.42]
}
```

坐标必须是归一化 `[x1, y1, x2, y2]`。本地代码验证：

- 四个有限数字且都在 `0..1`；
- `x2 > x1`、`y2 > y1`；
- 面积不能过小或接近整页；
- 同页记录总体保持从上到下顺序；
- 相邻记录不得出现不合理的大面积重叠。

模型坐标只作为定位候选，不是正式业务证据值。

### 5.2 本地候选

本地定位使用已经持久化的 OCR/layout 信息：

- 圈号、数字配方序号或“配方”标题行；
- 紧邻配方下方的日期行；
- 材料名称行与数量行；
- 明确“工艺”行；
- 相邻配方锚点的垂直中点；
- 页面内容总包围盒与公式顺序。

日期文本即使 OCR 字符有误，只要位置和日期形态仍可判断，也只能用于划分区域，
不得用来改写日期字段。

### 5.3 候选融合与回退

1. 模型候选和本地候选都有效且相互一致：取能完整覆盖两者的安全并集。
2. 只有一个候选有效：使用该候选。
3. 两者明显冲突：使用覆盖两者的较大安全区域。
4. 两者都无效：使用页面内容区域；内容区域也不可用时展示整图。

最终区域四周增加 8%–12% 上下文边距并限制在原图内。回退是正常降级，不在界面
显示“裁剪待确认”等额外文案；用户仍可通过“查看整图”判断证据。

### 5.4 证据产物

每条配方生成：

```text
review/evidence/<safe_formula_id>.jpg
review/evidence_regions.json
```

manifest 至少记录：

- formula ID；
- source image index；
- 原图相对路径和 SHA-256；
- 归一化区域与像素区域；
- 定位来源：`model`、`local`、`hybrid` 或 `full_image`；
- 裁剪图相对路径和 SHA-256。

裁剪从原始上传图生成，使用高质量 JPEG，避免再次使用发送给 VLM 的低质量缩略图。
所有路径都由 Job/formula 身份映射生成，不接受调用方提供任意文件路径。

## 6. 审查页面方案 A

### 6.1 桌面端

每条配方仍是一张业务卡片：

- 左列约 42%：当前配方裁剪证据；
- 右列约 58%：配方、日期、材料、数量、工艺、备注；
- 左列在当前卡片范围内 `position: sticky`；
- 修复卡片祖先的 overflow 约束，卡片圆角改由内部标题和内容层承担；
- 裁剪图声明宽高或 aspect ratio，避免页面加载跳动；
- 提供有文字标签的“查看整图”，支持键盘操作和可见焦点。

sticky 只跟随当前配方卡片；进入下一条配方时自然切换到下一张证据，不实现一个
跨全页面自动切图的全局侧栏。

### 6.2 窄屏

在小于 900px 的布局中：

- 证据图位于编辑器顶部；
- 取消 sticky；
- 不创建嵌套滚动区域；
- 字段和操作按钮保持至少 44px 可操作高度。

## 7. 日期原文与机器排序

### 7.1 展示与业务值

`FinalResult.record_date.value` 继续保存原始写法，例如：

```text
24.7.19
22/9/27
```

审查页把日期控件改为普通文本输入，不再使用只接受 ISO 的 `type=date`。Excel 导出
继续使用原始写法。

### 7.2 解析规则

内部日期解析器：

- 接受 `.`、`/`、`-`；
- 接受两位或四位年份；
- 两位年份按 `20xx` 解析；
- 月、日允许一位或两位；
- 使用真实日历严格验证；
- 不使用历史知识替换日期。

示例：

```text
24.7.19  → 2024-07-19
22/9/27  → 2022-09-27
2024-7-9 → 2024-07-09
```

无法解析时保留原文，内部排序值为空，并要求人工确认日期字段；空日期仍允许用户按
既有产品规则明确确认为空。

### 7.3 知识库兼容迁移

逻辑模型包含：

```text
record_date_raw   用户原文
record_date_sort  ISO排序值或NULL
date_status       KNOWN / UNKNOWN / UNPARSED
source_order      同一来源中的原始顺序
```

为减少数据库破坏：

- 现有 `formulas.record_date` 继续作为 ISO 排序列使用；
- 新增 `record_date_raw` 保存原文；
- API/代码层把现有 `record_date` 显式命名为 `record_date_sort`；
- 旧数据迁移时，把原 `record_date` 复制到 `record_date_raw`；可解析值同时规范到
  排序列，不可解析值把排序列设为 NULL，状态设为 `UNPARSED`；
- 迁移前沿用现有自动备份规则。

### 7.4 无日期记录排序

- 已知日期按内部 ISO 值排序；
- 同一来源中，日期缺失但处于两条已知日期之间的记录，依据 `source_order` 保留在
  两条记录之间；内部仅计算排序 rank，不编造日期；
- 只有单侧已知日期时，按来源顺序放在该锚点之前或之后；
- 完全没有日期锚点时，使用录入时间和 `source_order`；
- 用户修改日期后立即重新解析并重建排序 rank。

## 8. 错误与安全边界

- 裁剪生成失败不得使识别 Job 失败。
- 缺失裁剪图时审查 API 自动返回整图 URL。
- 原图或裁剪图 SHA 不匹配时拒绝使用该裁剪，并回退整图。
- 证据接口只接受已存在的 Job 和 formula ID，并验证解析路径仍在 Job 目录内。
- 不把原图、裁剪图、API Key、完整模型响应或私人路径写入公共日志、PR 或审计报告。
- 日期解析错误不静默清空或改写用户原文。
- amount、date、formula_no、identifier、unit 继续禁止历史知识自动覆盖。

## 9. 测试与验收 Gate

### 9.1 日期

- `24.7.19`、`22/9/27`、四位年份、三种分隔符；
- 非法日期、空日期、不可解析原文；
- 编辑日期后内部排序值重算；
- 原文在 UI、FinalResult 和 Excel 中不变；
- 知识库按内部日期排序；
- 同一来源的无日期记录保持在相邻有日期记录之间；
- 数据库迁移备份、旧值保留和回滚安全。

### 9.2 裁剪

- 模型 bbox 正常、越界、反向、过小、过大、重叠和乱序；
- 模型 bbox 缺失时本地回退；
- 模型与本地冲突时生成较大安全区域；
- 双方无效时回退整图；
- 上下文边距和边界 clamp；
- formula/source image/裁剪 SHA 的绑定；
- 证据路径穿越和错误 formula ID 被拒绝。

### 9.3 UI

- 长配方编辑时左侧证据保持可见；
- sticky 不越过当前配方卡片；
- “查看整图”可用且键盘可达；
- 1440px、900px 和 375px 宽度无横向滚动；
- 窄屏没有嵌套滚动；
- 日期原文不会因控件格式而消失。

### 9.4 真实 Gate

使用现有两张真实图片和 7 条配方验证：

- 7 条配方均获得正确来源图片和可用证据区域；
- 每条裁剪包含配方标题/序号、第二排日期、材料与数量，必要时包含工艺；
- 数字细节可放大核对；
- 用户逐条确认后进入 READY；
- 知识写回保留原始日期并使用内部日期排序；
- 正式 Excel 成功生成且日期仍为原写法。

完整自动化、Ruff、diff check、Secret 扫描和独立 GPT 复审继续作为 PR Gate。
